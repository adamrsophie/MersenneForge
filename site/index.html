Checked primality tests for Mersenne numbers, in Rust.

MersenneForge runs Lucas-Lehmer and base 3 probable prime tests of Mp = 2p − 1 with Gerbicz error checking, verifiable PRP proofs, and crash safe checkpoints, on the CPU or the GPU.

Design

One protocol, many kinds of arithmetic

The test protocols are written once over a small arithmetic interface. A backend only squares, multiplies, and moves residues; Rust owns everything that decides whether a result is right.

Errors caught, not hidden

Gerbicz checks with rollback for PRP, the Jacobi check for LL, roundoff checks on the DWT, coefficient bound checks on the GPU, and a stop after repeated failures.

Durable by default

Atomic, versioned, hashed checkpoints bound to the build and backend, file locks, a fsynced result journal, and a queue that only drops a line once its result is on disk.

Pure Rust

No upstream code and no linked native library. GPU kernels are WGSL and CUDA C written here. Protocol semantics and the proof format follow PRPLL (gpuowl).

Install

Get MersenneForge

Prebuilt binaries for Apple Silicon Macs and x86_64 Linux, or a build from source on any platform Rust supports.

Build
Apple Silicon (aarch64)

  1. Download the archive and the checksum list, and check the archive.

    U=https://github.com/adamrsophie/MersenneForge/releases/download/v0.2.0
F=mersenne-forge-v0.2.0-aarch64-apple-darwin-gpu
curl -LO "$U/$F.tar.gz" -O "$U/SHA256SUMS"
grep "$F" SHA256SUMS | shasum -a 256 -c

    The last line must print OK.

  2. Unpack it and put the binary on your PATH.

    F=mersenne-forge-v0.2.0-aarch64-apple-darwin-gpu
tar xzf "$F.tar.gz"
sudo install -m 755 "$F/mersenne-forge" /usr/local/bin/

    The binary is not signed or notarized, so macOS refuses an archive downloaded with a browser ("Apple could not verify ... is free of malware"). curl downloads are not quarantined. After a browser download, clear the flag on the unpacked binary, then install it:

    xattr -dr com.apple.quarantine "$F"

  3. Check the install against known answers.

    mersenne-forge doctor
mersenne-forge selftest --backend dwt

  1. Download the archive and the checksum list, and check the archive.

F=mersenne-forge-v0.2.0-x86_64-unknown-linux-gnu-gpu
curl -LO "$U/$F.tar.gz" -O "$U/SHA256SUMS"
grep "$F" SHA256SUMS | sha256sum -c

    The last line must print OK.

  2. Unpack it and put the binary on your PATH.

    F=mersenne-forge-v0.2.0-x86_64-unknown-linux-gnu-gpu
tar xzf "$F.tar.gz"
sudo install -m 755 "$F/mersenne-forge" /usr/local/bin/

    The GPU build needs a Vulkan driver and loader (for example the vendor driver, or Mesa with libvulkan1). vulkaninfo --summary shows what is installed. A software rasterizer such as llvmpipe is refused unless MERSENNE_FORGE_ALLOW_SOFTWARE_GPU=1 is set. Binaries are built on GitHub's current Ubuntu runner; on an older distribution, build from source.

  3. Check the install against known answers.

    mersenne-forge doctor
mersenne-forge selftest --backend dwt

  1. Install Rust 1.89 or newer with rustup, then fetch the tagged source.

    git clone https://github.com/adamrsophie/MersenneForge.git
cd MersenneForge
git checkout v0.2.0

  2. Build the features you need. Every build has the cpu and dwt backends.

    cargo build --release --locked                    # cpu and dwt
cargo build --release --locked --features gpu     # + wgpu: Metal, Vulkan, DX12
cargo build --release --locked --features cuda    # + CUDA (loads libcuda and NVRTC at run time)

    The binary is target/release/mersenne-forge. The CUDA build compiles without a CUDA toolkit; the driver and NVRTC are needed only to run it.

  3. Run the test suite.

    cargo test --release --locked
cargo test --release --locked --features gpu --test gpu_backend -- --test-threads=1

Quick start

From one test to a work queue

Add --json to any command for machine readable output. GPU and CUDA runs need --budget; --device N picks the adapter.

Single tests

# Lucas-Lehmer with the Jacobi check
mersenne-forge run --test ll --exponent 4423 --backend cpu

# PRP on the GPU, with a proof
mersenne-forge run --test prp --exponent 1257787 --backend gpu \
  --proof-power 8 --proof-dir work/proof \
  --checkpoint-dir work/ckpt --budget 2h

# Continue after Ctrl-C or a budget stop
mersenne-forge resume --checkpoint work/ckpt/M1257787-prp.ckpt --budget 2h

# A second run with every bit rotated (shift count)
mersenne-forge run --test prp --exponent 44497 --shift 12345 --backend dwt

Queues and factoring

# Run a Prime95 style worktodo file
mersenne-forge work --worktodo worktodo.txt --results results.json.txt \
  --checkpoint-dir work/ckpt --proof-dir work/proof --backend gpu

# A local control page: progress, queue, results, devices
mersenne-forge ui --worktodo worktodo.txt --results results.json.txt \
  --checkpoint-dir work/ckpt

# Trial factoring, on the GPU below 2^95
mersenne-forge tf --exponent 100000007 --from 60 --to 70 --gpu

# P-1, P+1, ECM
mersenne-forge pm1 --exponent 67 --b1 1000 --b2 3000
mersenne-forge pp1 --exponent 67 --b1 2000 --b2 50000 --run 1
mersenne-forge ecm --exponent 67 --b1 2000 --curves 40

# How much factoring does an exponent deserve?
mersenne-forge policy --exponent 100000007 --tf-bits 77

Capabilities

Primality tests

  • PRP, base 3, Gerbicz checked, residue types 1 to 5; cofactor tests with known factors
  • LL with the Jacobi check, rewinding to the last verified residue
  • Proofs: format version 2, as PRPLL writes them; self verified after generation
  • CERT squarings with a SHA3-256 hash
  • Shift counts for PRP and LL, as Prime95 uses for double checks
  • k·bn+c PRP and Fermat Pépin tests on the host, to 220 bits

Factoring

  • Trial factoring with a sieve to 216 in mfaktc's 4620 classes; GPU kernel and device sieve below 295
  • P-1: stage 1 on any backend, paired stage 2 (D = 210), optional polynomial stage 2
  • P+1 and ECM (Montgomery curves, Suyama sigma) on the host; ECM stage 2 from GMP-ECM save files
  • Policy: P-1 bounds and trial factoring depth from a cost model
  • Every factor is checked to divide 2p−1 before it is reported

Reliability

  • Checkpoints written atomically, versioned, hashed, and bound to a SHA3-256 build identity
  • Portable checkpoint export to move a run between builds or backends
  • Locks on checkpoints, proof stores, worktodo, and results files
  • Result journal: an assignment leaves the queue only after its result is fsynced
  • Disk preflight for proof points; faults roll back, repeated faults stop

Interoperability

  • Prime95 worktodo grammar: PRP=, Test=, DoubleCheck=, Cert=, Factor=, Pminus1=, Pfactor=, Pplus1=, ECM=, ECMSTAGE2=
  • JSON result lines in PRPLL's form, with proof MD5
  • PrimeNet v5 client (register, fetch, submit, progress, unreserve) and manual forms
  • supervise runs one worker per device; ui serves a local control page that can add to the queue

Notes

Good to know

What does a PRP pass or an accepted proof mean?

A PRP pass means Mp is a base 3 probable prime. A proof accepted below p = 217 has had its terminal residue recomputed directly; above that, acceptance means the file satisfies the version 2 proof equation, which is sound against computation errors and skipped work but not against a prover who knows a factor of Mp.

No proof establishes that Mp is prime; an independent test does.

Can I move a run to another machine or backend?

Checkpoints are bound to the build and backend that wrote them. checkpoint-export writes the last verified state without that binding, and resume --backend continues it elsewhere. Proof files are portable across builds and backends.

Does work talk to PrimeNet?

No. work reads and writes local files only. The separate primenet-v5 and primenet commands contact mersenne.org, and only when you run them.

Why is the GPU backend refusing my device?

doctor lists the adapters and the plan for an exponent. The backend checks storage binding size, buffer size, storage buffers per stage, and workgroup size, and returns "unsupported" when a plan does not fit. Software rasterizers are refused unless MERSENNE_FORGE_ALLOW_SOFTWARE_GPU=1 is set.
